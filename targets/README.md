# Targets: one settings file per archive

The scripts in [`../scripts/`](../scripts/) were written for one Lean 4 archive. Everything in them that is a fact about that archive is now read from a *target profile*, a short settings file in this directory. The archive they were written for is the default target, `alpoge-rh`: with no target named, every script does what it did before profiles existed.

**State of this, on 2026-11-27:** the mechanism is tested offline, in about three minutes, by `scripts/dev/test_targets.sh`, on small made-up projects. For the default target that test uses a made-up stand-in for its tarball. On the real tarball, only the archive listing and entry checks have been run with these changes, and their output was the same as before, under Python 3.14 and under macOS's own Python 3.9. Those checks now include one that nothing but zero bytes follows the end of the archive; the real tarball passes it, so the listing recorded for it before saw every entry. The full pipeline (build, axiom check, kernel replay) has not been run again on the default target since profiles were added. On the archive of the second profile here, `grh-compact`, the steps that compile nothing were run on 2026-11-27: 01 to 03 and the import graph (794 source files; the records are in [`grh-compact/records/`](grh-compact/records/)). The first attempt was refused at step 02, because the archive's lakefile declares a library outside its sources; the setting `TGT_LIBS_OUTSIDE_SRC` was added for it, and the steps were then run to the end. The same day the whole pipeline was run on it once, on a rented 16-vCPU machine, after a rehearsal on a smaller one: 794 of 794 modules built in 32 minutes, step 08 and its `--deep` walk passed, and `leanchecker` passed every module (step 09 with `--c3`); the two runs cost 0.61 USD at the ledger's rates ([`../records/cloud/target-runs/`](../records/cloud/target-runs/)). That is one run of this repository's own steps, by one user on the machine. It is not the set of checks in the community's record of that proof: no export, no independently written kernel and no Comparator were run on it here. No step from 04 on has been run on it on a laptop. The cloud scripts in `cloud/gcp/` know only the default target, apart from the two modes that made those runs (`target` and `target-rehearsal`).

## Choosing a target

```bash
scripts/verify.sh                               # the default target, alpoge-rh
RH_TARGET=grh-compact scripts/verify.sh         # another profile, for one command
```

`RH_TARGET` can also be set in `config.env`. A value in the environment wins over `config.env`. A target's name is the name of its directory here: lower-case letters, digits and `-`, not starting with `-`.

A profile is the file `targets/<name>/target.env`. For any target but the default one it is sourced as shell code by `scripts/lib.sh` and may only assign the variables listed below (`lib.sh` sets `LAKE_NO_CACHE` and unsets the git and Lake variables it names after it has read the profile, so a line that sets one of them does not reach the programs the scripts run, or stops the scripts). A profile for such a target inherits nothing from the default one: it must set every variable marked *required*, or the scripts stop and name the one that is missing, and the others are then empty or as the last column says.

The default target's profile, `alpoge-rh/target.env`, is **not read**. Its values are built into `scripts/lib.sh`, so that the scripts work as they did before profiles existed; the file repeats them for reference, and a test checks that the two agree. To change one of them, change both, or set the variable in `config.env` or in the environment, where it wins over the built-in value: `RH_PART_URL_PREFIX=<a mirror> scripts/01_fetch.sh`, for example.

## One working directory per target

A working directory holds one extracted archive, one build and its logs, and nothing in it used to say whose they were. Three rules now keep targets apart.

- **The directory.** For the default target the working directory is `RH_WORKDIR`, as before. For any other target it is `RH_WORKDIR` with `-<target name>` added (`work` becomes `work-grh-compact`), unless `RH_WORKDIR` was given in the environment for that command, in which case it is used as given.
- **The marker.** The first script that creates anything in a working directory writes the target's name to the file `.rh-target` there (into a file of its own, `.rh-target.<number>`, which it then links to `.rh-target`, so that the marker never exists without the name in it). Every script stops if that file names another target. A directory with files in it and no marker is taken to belong to the default target, and any other target refuses to use it.
- **The extracted tree.** For any target but the default one, `02_inspect_and_extract.sh` writes a line naming the source it extracted to `extract.from` in the working directory: the archive's SHA-256 and, for a `git` source, the address, commit, directory and prefix. It writes the line before it moves the tree into place. It uses an extracted tree again only if that line is the one that the archive there now and the profile give, and steps 03, 04, 05, 08 and 09, and `reproduce_findings.sh`, stop if it is not the one the profile gives now. The whole line is compared, pinned or not, so a change to any part of it means extracting again, even one that leaves the archive the same byte for byte (the address of a mirror, or a commit that changes nothing in the directory). Moving the extracted tree aside moves its compiled files with it, but not the rest of the build's record: the build logs (`logs/`) and the kernel replay's results (`analysis/kernel_replay/results.tsv`) stay in the working directory, and `06_progress.sh` and `09_kernel_replay.sh` read them.
- **An empty marker.** If `.rh-target` is empty or cannot be read, the scripts stop and say how to write the target's name into it. If it is a symbolic link, or not a plain file at all (a directory, say), they stop and say how to put a plain file in its place: a link has to be removed first (`rm -- <marker>`), since writing to it would change the file it points to, which may be another working directory's marker. A script that cannot write the name (a full disk, say) removes its own file, says so and stops, and leaves no marker. On a file system with no hard links (some network shares) the marker is written in place instead, and a script started at the same moment as the one writing it can find it still empty and stop; run it again.
- **The file system.** For any target but the default one, the working directory must be on a file system with Unix permissions, such as APFS, HFS+ or ext4. On FAT or exFAT every file reads as executable, and macOS writes a `._` file beside each file it writes, so `02_inspect_and_extract.sh` finds what `tar` wrote different from the listing every time and never puts the tree in place.

### After a change of commit

1. Empty `TGT_TARBALL_SHA256` in the profile: the value pinned for the old commit is refused for the new one.
2. Move aside, rather than delete if you want to keep the old commit's results, the extracted tree (`extract`), the logs (`logs`) and the analysis results (`analysis`) in the working directory, and the target's records (`targets/<name>/records`). Simpler still: use a fresh working directory (`RH_WORKDIR=<new directory>` in the environment for every command), copying `download/` and the marker `.rh-target` into it if you want to keep the clone (`mkdir -p <new> && cp -R <old>/download <old>/.rh-target <new>/`; a directory with files in it and no marker is refused). The clone saves a download only if it already has the new commit; if it does not, step 3's `--redownload` replaces it anyway. Left in place, the old commit's build logs and kernel replay results are read as the new commit's. The old records must be out of the way too: `02_inspect_and_extract.sh --write-expected` writes nothing while a run differs from an existing record, and `03_audit_source.sh --write-expected` stops only when a category recorded as zero has matches; any other difference is reported and the audit section replaced, unless `--strict` is given.
3. Run `scripts/01_fetch.sh`, with `--redownload` if the clone was made before the new commit was published. A change of address also needs `--redownload`: a clone made from another address is not used.
4. Do steps 3 to 6 of [Adding a target](#adding-a-target) again, pinning the SHA-256 that `01_fetch.sh` prints.

### What the archive checks refuse

Whatever the profile says, `02_inspect_and_extract.sh` refuses an archive with any of these before it extracts anything. The listing that these checks are made on is the archive as Python's `tarfile` reads it; the `tar` that extracts it may read some headers differently. The headers on which `tarfile` and other tars are known to disagree, and which the listing can see, are refused (the list below), so that the two find the same entries in the same places. That cannot be known to be every disagreement there is, so for any target but the default one the extracted tree is also compared with the listing afterwards (below), and that comparison is what makes sure the tree holds what the listing checked. The default target relies on its pinned SHA-256 and its recorded listing instead.

- an entry that is not a regular file: a directory entry, a symbolic or hard link, a device, a fifo;
- an executable bit (unless `TGT_ARCHIVE_ALLOW_EXEC=1`), or a setuid, setgid or sticky bit;
- an absolute name, an empty, `.` or `..` component, a backslash or a control character in a name, a name that is not UTF-8, a name outside the prefix;
- a name longer than 1024 bytes, or with a component longer than 255 bytes (macOS's limits);
- two entries with one name, or a file where another entry needs a directory;
- a `.git` or `.lake` component, also when spelled in the other ways git refuses for `.git`: in another case, with characters HFS+ ignores, with dots or spaces at the end, followed by an NTFS stream name, or as `git~1` (`lake~1`);
- a file named `HEAD`, in any of those spellings: git takes any directory that holds a `HEAD` file beside `objects/` and `refs/` for a repository, whatever its name, and obeys the configuration in it (a command it runs on `git status`, for example), so refusing `.git` alone would not keep a repository out of the tree;
- a header that tars are known to read differently: a header in neither POSIX ustar format (which pax archives use) nor GNU tar's, so an archive in the old v7 format is refused (bsdtar recognises an archive by its first bytes, and without the format's mark may read it as another format); a checksum field that is not plain octal digits or does not match the header (bsdtar skips such a header and reads on in what `tarfile` took for its data); a number field (mode, user and group id, size, time, device numbers) that is not octal digits with spaces before them and spaces or NUL bytes after them, nor base 256 below 2^63, or, for a time, a negative number in base 256 (bsdtar takes a first header with another form for something that is not tar, and may then read the archive as another format); a text field (name, link name, user and group name, name prefix) with a control character in it, or with anything but NUL bytes after the NUL that ends it; a first header that begins as a bzip2, xz or zstd stream does (bsdtar would decompress it and read what came out; with the rules before, no header can begin as bsdtar recognises its other compressed formats or uuencoded data, each of which needs a control character, or a NUL byte with other bytes after it, near its start); bytes in the part of a header in GNU format where a POSIX header has its name prefix (bytes 345 to 499: `tarfile` puts them in front of the name, and bsdtar reads GNU tar's access and change times, its old map of a sparse file and its real size there, for an entry of any kind), a GNU long name that runs past the size its header gives, pax data that is not whole records ending at the size its header gives, or with anything but zero bytes in the rest of its block (`tarfile` reads records there, other tars do not), two extended headers of one kind before one entry (two pax headers, two long names or two long link names: `tarfile` uses the first, bsdtar the last), more than 8 extended headers in a row, an extended header larger than 512 KiB, a sparse entry (GNU's type `S`, or the pax keys `GNU.sparse.*` and `SCHILY.realsize`: `tarfile` reads a sparse file's map of holes with no limit, and tars read sparse files differently), Solaris's pax keys (`SUN.*`: bsdtar applies them, and `SUN.holesdata` makes holes in the file that `tarfile` does not see), a pax `size` that is not plain digits, a pax `path` that ends in `/`, the pax keys of an access control list, a global pax header that sets anything but a comment, or an extended header of an unexpected type before an entry's own;
- an AppleDouble file, whose name starts with `._`: macOS's tar does not write it but applies what it holds, as extended attributes and an access control list, to the entry that follows it in the archive, whatever that entry's name. macOS's tar adds one for each file that has extended attributes unless `COPYFILE_DISABLE=1` is set when it makes the archive. A published, pinned tarball with such files has to be made again by whoever publishes it, and a `git` source that has one committed can be used only once it is removed from the commit;
- two names that are one on a file system that ignores case and Unicode normalisation, as macOS's does by default, or a character the Unicode tables of the Python in use do not know (its folding is then unknown);
- anything but zero bytes after the end of the archive, or an archive that cannot be read to its end (a damaged header, a wrong gzip checksum, compression other than gzip, a gzip member with the flags gzip reserves set, or, after a gzip member, zero bytes followed by anything or bytes that are not another member: Python's `gzip` skips zero bytes between members and ignores the reserved flags, and bsdtar stops at either). The tar that extracts an archive may carry on past such a place and find entries there that the listing never saw.

For any target but the default one, what `tar` wrote is then compared with the listing before the tree is put in place. Everything in it, `.lake` included, must be an entry the listing checked, or a directory on the way to one, with no links and no other files, no executable bit (unless `TGT_ARCHIVE_ALLOW_EXEC=1`) and no setuid, setgid or sticky bit, and holding the entry's bytes exactly (the other permission bits are not compared: `tar` applies the umask to them). The project files are then read as in step 4 of the script. Only if all of that passes is the tree put in place; otherwise it is left in `extract.partial` and nothing in it is used. (The default target's archive is pinned and its listing recorded, so this is not done for it.) For these targets 02 also unsets `TAR_OPTIONS` (GNU tar's) and `TAR_READER_OPTIONS` and `TAR_WRITER_OPTIONS` (bsdtar's), so that options in the environment cannot change how `tar` extracts.

Reading the project files (02's step 4, for every target, the default one included, and again by `04_setup_toolchain.sh` before it runs anything) refuses:

- a `lakefile.toml`, `lake-manifest.json` or `lean-toolchain` that is not UTF-8 text, and a manifest that is not JSON Python can read, that nests its values more than 32 deep, that has a number of more than 30 digits, or that has `NaN` or `Infinity` (Python reads them; they are not JSON);
- a manifest not in the form Lake writes (an object whose `packages` is a list of objects; Lake also reads one with no `packages`, this does not), with no version Lake 4.33.1 reads (`version`, or `schemaVersion`, of at least 0.5 and below 2; a `-` after its three numbers must have something after it), or with a package in another form than the one of its version (`{"git": {...}}` before version 7, a flat object from it): Lake stops at either, so what is printed could not show what it would read. Lake also stops at a manifest missing a field it needs, and then fetches nothing; that is not checked, so a manifest this accepts can still be refused by Lake;
- a `path` package (Lake runs the lakefile in its directory, which nothing here reads), a `packagesDir` other than `.lake/packages`, and a package whose `configFile` is not `lakefile`, `lakefile.lean` or `lakefile.toml`, whose `manifestFile` is not `lake-manifest.json`, or that has a `subDir` (other than `.`). Lake joins these to a directory with no check that the result stays inside it, so another value could name a file of the archive as the lakefile of a package whose address you trust; and with a `subDir`, Lake would take the package from that directory of its clone, while 04 looks for a prebuilt build Lake downloaded at the top of each clone;
- a package name not written as Lake writes it. Lake reads a name as Lean does, dropping guillemets, so `«mathlib»` is the name `mathlib`, and a manifest could give Mathlib twice in two spellings while a check of the text saw two packages. So a name with guillemets around an identifier is refused, as is one with a part that is not an identifier, a number or between guillemets (`doc-gen4` with none: Lake cannot read it), or with a number with a zero before it. Between guillemets only ASCII letters, digits and `_'!?+-` are accepted, as in a lakefile's names: Lake keeps a package in `.lake/packages/<name>`, the name with its guillemets dropped, and, as with the values above, does not check that this is one directory there (`«../x»` would be outside it, and so would the clone 04 makes). Refused too are two packages of one name (Lake uses the last); two whose directories are one, the name with its guillemets dropped and compared without regard to case (`1`, a number, and `«1»`, a string, are two names kept in one directory, and on a file system that does not tell upper from lower case, as APFS and NTFS by default, so are `mathlib` and `Mathlib`); a name too long for the clone 04 makes beside its directory; and a manifest with no package named `mathlib`;
- any toolchain, package name, git package's revision or address that is missing (whether or not the addresses are listed) or is not printable ASCII or has a space in it, and a requirement's `scope`, `git`, `rev` or `version` in `lakefile.toml` that is not printable ASCII or has a space in it: such characters could hide what follows them on a terminal, look blank or look like other letters (a host `gіthub.com` with a Cyrillic `і`). A package name may have the guillemets Lake writes around a part that is not an identifier (`«doc-gen4»`). The `lean-toolchain` file may end with line ends, but nothing else is taken off it;
- a `lean-toolchain` that does not name a release by its tag, `v<major>.<minor>.<patch>` with `-rc<n>` after it or not, the `v` optional (`leanprover/lean4:v4.33.1`, `v4.33.1` alone, or `leanprover/lean4:4.33.1` as Lake writes the line when no elan runs it; elan puts the `v` in): elan fetches a nightly from another repository than the one named (`leanprover/lean4-nightly` for `leanprover/lean4`), resolves `stable`, `beta` and `nightly` over the network, and runs a toolchain linked under another name from wherever it was linked; it would fetch and install such a toolchain as soon as 04 asked it which `lean` it would run, before 04 could compare anything. Refused too are an origin, the part before the colon, that is not `<owner>/<repository>` of ASCII letters, digits, `_` and `-` (elan reads one that is not as a path, or not at all), and a project with a file or directory named as the line's first part (`leanprover`, or `v4.33.1` for a line with no origin): elan 4.2 reads the line as a path in the project first, a release tag included, and runs `<line>/bin/lean` from the project if there is one, so the archive's own `lean`, `lake` and `leanchecker` would run. With elan, 04 also checks that the `lean` elan chose is the release's own, in elan's `toolchains` directory (a relative or empty `ELAN_HOME` is refused, by 05 and 08 too: elan would read it against the project's directory; so is one under the work directory's `extract`, where the archive is), and step 09 takes `leanchecker` only from there. The `lean` and `lake` that 04, 05 and 08 run are the first on `PATH`, normally elan's own, which run what elan chose;
- a git package whose revision is not a full commit hash (40 hexadecimal digits, as Lake writes the commit it checked out), whose address is not of the form `https://<host>/<path>` with a path of plain parts (ASCII letters, digits and `_.~+-`, none of them `.` or `..`; a port may follow the host), or that has no `type`, and a requirement in `lakefile.toml` whose `git` is not of that form. Lake resolves any other revision against the package's address each time it fetches the package (as a branch or tag of that name first), so the files would not name the commit it checks out. A full hash does not on its own either: Lake checks a commit out with `git checkout --detach <hash>`, which takes a branch of that name in the clone over the commit (a clone has one when it is the remote's default branch), does not compare what it checked out with the manifest, and runs the package's lakefile as soon as it has. So 04 clones each git package itself before Lake runs, from a directory of its own, and checks it out by `<hash>^{commit}`, which no branch can stand for; Lake then finds each package at its commit and neither fetches nor checks out anything. 04 clones and checks each package under a name of its own (`.lake/packages/.<name>.rhv-partial`, removed when 04 runs again if a run stops half way) and only then renames it. It stops if a package directory is already there at another commit or with files that are not as in that commit, and checks every package again after each time its Lake has run, as it checks that the manifest has not changed. It compares the files git tracks with the commit, through the clone's index (with `git status`, which writes nothing), with no replacement refs and whatever `core.ignoreStat` or an fsmonitor would say, and it refuses a file git is told not to look at (assume-unchanged or skip-worktree); files git does not track, a package's `.lake` among them, are not looked at. It checks its own clones out with no line ends changed, no `$Id$` filled in and no filter run, whatever a package's `.gitattributes` says. git reads an address with no scheme as a directory, which could be one of the archive's own files (a git bundle stored at `lean/github.com/leanprover-community/mathlib4` would be cloned while the address shown reads as GitHub's), and Lake passes the address to git as it is; `file://`, `ssh://`, `user@host:path` and an address with a user name before the host are refused too, and so are `.` and `..` parts, which git's https transport takes out of the path before it sends the request (`https://github.com/leanprover-community/mathlib4/../../other/x` fetches `github.com/other/x`), and `%`, `?`, `#` and empty parts (a closing `/` is allowed). The scheme does not stop git from reading an address as a path: `git clone` reads it as a path in the directory it runs in first (`https://github.com/x/y` is the path `https:/github.com/x/y`, with `.git` or `.bundle` after it or not), and Lake runs it in the project's directory. So a project with a file or directory named `https:` is refused too, and 04 clones from a directory of its own. Lake stops at a package with no `type`;
- a `lakefile.toml` outside the part of TOML that lakefiles are written in (the headers `[leanOptions]`, `[[require]]` and `[[lean_lib]]`; bare dotted keys; strings on one line with no backslash; whole numbers, `true`, `false`, arrays, and inline tables on one line), with a key given twice, or with any key but those of a package's name, version, description, keywords, homepage, license, `srcDir`, `defaultTargets`, `moreLeanArgs`, `weakLeanArgs` and `leanOptions`, of a requirement's `name`, `scope`, `git`, `rev` and `version`, and of a library's `name`, `srcDir`, `roots`, `globs`, `leanOptions`, `moreLeanArgs` and `weakLeanArgs`. So an executable (`[[lean_exe]]`) is refused: Lake builds and runs one by its name, and one called `cache` would be run in place of Mathlib's. So are arguments to `lean` other than `--tstack`, `--threads`, `--memory`, `--timeout` and `-D<option>=<value>` (`--plugin` and `--load-dynlib` load native code into `lean`), two requirements with one name, a requirement the manifest has no entry for (Lake stops at it), a package named as a package it depends on (Lake would leave that one out and use this one's code in its place), and a library whose sources are not under `TGT_SRC_DIR`, the directory step 03 reads (`./src` and `src/` are read as `src`). The one exception is a library the profile names in `TGT_LIBS_OUTSIDE_SRC`, which is accepted only as a library the build does not compile, under the conditions given for that setting in the table above. A library's `srcDir` may go up with `..` parts (`srcDir = ".."` in a package whose `srcDir` is `src` is the project's own directory), but only as far as the project's directory: one that leaves it is refused, named in that setting or not. So, too, are Lean options, in `leanOptions` or as `-D<option>=<value>`, with `weak.` before them or not, other than `autoImplicit`, `relaxedAutoImplicit`, `maxHeartbeats`, `maxRecDepth`, `maxSynthPendingDepth`, `synthInstance.maxHeartbeats`, `synthInstance.maxSize`, `warningAsError`, `Elab.async` and those that start with `pp.`, `linter.` or `backward.`: some options make `lean` run a program (`sat.solver`, in any module that uses `bv_decide`), write a file (`trace.profiler.output`) or add declarations with no check by the kernel (`debug.skipKernelTC`). An option a project needs can be added to `LEAN_OPTIONS_ALLOWED` in `scripts/verify/rhv_tools.py` once what it does is known. Each part of a library's, target's or module's name is an identifier (an ASCII letter or `_`, then ASCII letters, digits and `_'!?`) or, as `lake new 2proj math` writes a part that is not one (`«2proj»`), ASCII letters, digits and `_'!?+-` between guillemets. A lakefile Lake reads can be refused by this; it is meant to be strict: quoted keys, digit separators (`1_000`) and a glob given as one string rather than a list are refused, though Lake reads them.
- a lakefile whose Mathlib `rev` is neither the commit the manifest's entry for `mathlib` has (`rev`) nor the revision that entry was made from (`inputRev`: the tag or branch, as `lake new <name> math` pins Mathlib by its tag): 02 and 04 print a WARNING and stop. Lake checks out the manifest's commit either way.

`00_check_prereqs.sh` and `04_setup_toolchain.sh` show the `lean-toolchain` line, its line end removed, with every byte that is not printable ASCII as `?`. Every script runs Lake with `LAKE_NO_CACHE=1` (`scripts/lib.sh` exports it, and stops if a program it runs would not get it), so Lake does not download a prebuilt build of a package before it builds one whose build directory is missing: not from Reservoir (`reservoir.lean-lang.org`, for a package whose scope is `leanprover` or `leanprover-community`), nor from a package's GitHub releases (when its lakefile sets `preferReleaseBuild`). Such a build is the package's whole build directory, programs included, and step 09 replays only the project's own modules, so nothing would check it. The setting stops only that download: a package's lakefile (a `lakefile.toml` too, with `needs = ["@<package>:release"]`) or a tool that asks Lake for a package's `release`, `barrel` or `cache` facet still has Lake download and unpack one, so look for those in the packages' lakefiles. 04 stops if it finds, after its own Lake runs, the trace of such a download where Lake writes it by default: in a package's `.lake` directory, at any depth outside its `build` directory, or in the project's, outside its `build`, `config` and `packages` directories (`<package>-<platform>.tar.gz.trace` for a release, `build.barrel.trace` for a barrel). `lakefile.olean.trace` at the top of a `.lake` directory is left out: an older Lake kept a package's compiled lakefile there. 04 also stops if there is a `.lake/package-overrides.json` before or after its Lake runs: Lake would take the packages it names from where it says, in place of the manifest's entries. A package's lakefile can have Lake put the archive elsewhere (`buildArchive`: in the build directory, outside `.lake`, or at an absolute path), which 04 does not find, so look for `buildArchive`, `releaseRepo`, `preferReleaseBuild` and `needs` in the packages' lakefiles. The build in step 05 is not checked. The default target's packages, at the commits pinned, ask for none. The compiled files of Mathlib and its dependencies come from Mathlib's cache tool, which does not read the setting. The cloud guest scripts for the default target in `cloud/gcp/` (the pilot, the full run, the export check and the kernel check) do not set it; `target_guest.sh`, for another target, runs the numbered scripts, which do. `04_setup_toolchain.sh` fetches Mathlib's cache with `lake exe mathlib/cache get`, which names the package the tool is in.

The comparison does not look at extended attributes, file flags or owners. An archive can give them (the pax keys `SCHILY.xattr.*`, `LIBARCHIVE.xattr.*` and `SCHILY.fflags`, which the listing accepts, since macOS's tar writes extended attributes into any archive it makes in pax format), but `tar` run as an ordinary user does not apply them, and for any target but the default one `02_inspect_and_extract.sh` will not extract when run as root.

As an extra safeguard while you read an extracted tree, you can tell git to use a bare repository only when you name it with `--git-dir` or `GIT_DIR`: `git config --global safe.bareRepository explicit` (the default from Git 3.0 on). It does not stop git from finding an ordinary repository (a `.git` directory) above the directory you are in.

A tarball made with `tar czf x.tar.gz lean` has directory entries in it and is refused. One made from a list of plain files, from a clean copy of the sources, is not: `find lean \( -name .git -o -name .lake \) -prune -o -type f -print | LC_ALL=C sort | COPYFILE_DISABLE=1 tar czf x.tar.gz -T -`. The `-prune` leaves out git's and Lake's directories, which are refused; `COPYFILE_DISABLE=1` stops macOS's tar from adding `._` files. The files must be plain copies, since tar stores a second name of a hard-linked file as a link, and they must have no executable bits unless `TGT_ARCHIVE_ALLOW_EXEC=1`.

## Adding a target

1. Make `targets/<name>/target.env`; `<name>` may use lower-case letters, digits and `-`, and may not start with `-`. Start from [`grh-compact/target.env`](grh-compact/target.env) for a git repository or [`alpoge-rh/target.env`](alpoge-rh/target.env) for a tarball. Every value in the first is that archive's, so in a copy of it change the address, commit, directory, prefix and source directory, empty `TGT_TARBALL_SHA256` (step 3 prints the value to put there), set `TGT_RECORDS_DIR` to `targets/<name>/records` (kept as it is, the new target would be compared with that archive's records), change the module, theorem and statement names and the smoke modules, and empty `TGT_LIBS_OUTSIDE_SRC` or set it for your own lakefile (as it is, it names a library of that archive). Every value in the second is the default target's, so in a copy of it change the address, count, SHA-256 and name of the parts and tarball, the prefix and source directory, `TGT_RECORDS_DIR` (to `targets/<name>/records`: kept as it is, the new target would be compared with the default target's records) and the module, theorem and statement names; and empty `TGT_PROBE_MODULE`, `TGT_PROBE_THEOREM`, `TGT_MATHLIB_TAG`, `TGT_S10_PATTERN` and `TGT_S10_COUNT` unless they mean something for your archive. A lakefile that is a program (`lakefile.lean`) is not supported: read it yourself first. It is not the only code the archive chooses: see step 4.
2. Name the target for every command that follows: `export RH_TARGET=<name>` in the shell you use (or put `RH_TARGET=<name>` in `config.env`). A command run without it works on the default target.
3. Fetch the source. This differs by kind.
   - **`git`:** leave `TGT_TARBALL_SHA256` empty and run `scripts/01_fetch.sh`. It writes the tar file and prints its SHA-256 under a line in capitals that says it is NOT PINNED. Put that value into the profile as `TGT_TARBALL_SHA256`, then run `scripts/01_fetch.sh --check-only` to see it compared. Pinned or not, the scripts use the tar file only if `01_fetch.sh`'s record beside it (`download/source.tar.from`) names the address, commit, directory and prefix the profile names: the SHA-256 says which bytes the file has, and only the record says which commit they are.
   - **`tarball-parts`:** the profile must give the SHA-256 of the whole tarball before anything is fetched. Take it from where the tarball is published if it is given there. If you compute it yourself from the parts you downloaded, nothing but your own download vouches for it: say so wherever you report the result. Then run `scripts/01_fetch.sh`. It writes the SHA-256 of each part to `download/parts.sha256`. Copy that file into the records, so that later runs compare every part as well as the whole: `mkdir -p targets/<name>/records && cp "$(bash -c '. scripts/lib.sh && printf %s "$RH_DL"')/parts.sha256" targets/<name>/records/`.
4. `scripts/02_inspect_and_extract.sh --write-expected targets/<name>/records/expected.json`. The first run has nothing recorded to compare with and says so in capitals. Read the listing and the entry check before going on: what is recorded now is what later runs are compared with. `--write-expected` records nothing when a run differs from a record that is already there. Read also the lines under "where step 04 fetches and runs code from", which 02 prints for any target but the default one. Step 04 runs code that the archive chooses even without a `lakefile.lean`: elan installs and runs the toolchain that `lean-toolchain` names (the part before the colon is a GitHub repository, and 02 marks one that is not `leanprover/lean4`; the part after it must be a release tag, and the project may have no file at the line's path, which elan would run instead), 04 clones every package at the address in `lake-manifest.json`, and Lake runs its lakefile (Mathlib's is a `lakefile.lean`) and builds and runs Mathlib's cache tool. The project's own `lakefile.toml` decides what Lake builds and with which options to `lean`; what it may say is limited (above), and step 03 scans only the sources under `TGT_SRC_DIR`. Step 05 then compiles those packages, which step 03 does not audit. Go on to step 04 only if the toolchain is `leanprover/lean4` and every address is one you trust.
5. `scripts/03_audit_source.sh --write-expected targets/<name>/records/expected.json`. Read what it lists in each category: the record says only that later runs find the same.
6. `python3 analysis/import_graph.py`, then copy the summary it made into the records: `cp "$(bash -c '. scripts/lib.sh && printf %s "$RH_AN"')/import_graph_summary.json" targets/<name>/records/`. With steps 4, 5 and 6 done, `scripts/reproduce_findings.sh` compares everything it can with the records.
7. Level 2 and beyond of [`../docs/replication-guide.md`](../docs/replication-guide.md). That guide is written for the default target. For another one, skip `08_check_axioms.sh --probe` unless the profile sets `TGT_PROBE_MODULE` and `TGT_PROBE_THEOREM`; where it builds or imports the default target's modules by hand, use the modules of `TGT_SMOKE_TARGETS` and `TGT_ROOT_MODULE`; and read its sizes and timings as the default target's.

## What a `git` source becomes

`01_fetch.sh` clones the repository without checking anything out, confirms that the commit named is in it, and writes the files of that commit (or of `TGT_GIT_SUBDIR` in it) to a tar file: every blob byte for byte as git stores it, names in sorted order, no times, no owners. Symbolic links, submodules, `.git` and `.lake` components, files named `HEAD` and names that collide on macOS are refused, and every blob's SHA-1 is computed again from what is written. So is a commit whose trees name more than 2,000,000 entries, files and directories, a directory counted each time it is named, or more than 64 GiB of files (`rhv_tools.py git-export --max-files`, `--max-bytes`), or whose paths come to more than 256 MiB. Each tree is read from git once, however many times the commit names it (up to 64 MiB of trees are kept), so that a repository of a few kilobytes naming the same few trees two million times is refused in seconds. These limits bound the work of `git-export` itself, not git's: git builds each object it gives from the deltas it is stored as, and a repository made for it can make that slow (a long chain of deltas) or take a lot of memory (a small tree stored as a delta against a very large object), and `01_fetch.sh` has git read the commit before `git-export` looks at its size. Clone only repositories you are prepared to have git read. Only repositories that name their objects by SHA-1 are supported; one that uses SHA-256 is refused. The same commit gives the same tar file on any machine, so its SHA-256 can be recorded and compared like a published tarball's. Beside it, `01_fetch.sh` writes `<tar file>.from`, a line that names the address, commit, directory and prefix it was written from; the line is removed before the file is written again and put back only once the file is complete. The clone records the address it was made from (`git config rhv.sourceurl`), and a clone made from another address than the profile's is not used. From there on a `git` source is handled exactly as a tarball is: listed and checked entry by entry before anything is extracted.

`git archive` and `git checkout` are not used for this, because both can change file contents according to attribute files inside the repository.

## What is not covered

- The cloud modes of the default target (`cloud/gcp/`: the pilot, the full run, the export check, the kernel check) and the cost models in `analysis/`. Two other modes run the numbered steps, with the import graph and `reproduce_findings.sh`, and none of those checks, for another target on one machine ([`../cloud/gcp/README.md`](../cloud/gcp/README.md), "Another target").
- A project with a source file whose name has a dot inside a part of its path (Lake reads `X.Y.lean` as the module `«X.Y»`), or with two files that would have one module name: step 09 counts such files as a fault and never says the replay is complete.
- A working directory on FAT or exFAT, and extracting as root, for any target but the default one (see above).
- A project whose sources are not under one directory, or that is configured by `lakefile.lean`.
- A project that does not depend on Mathlib: `04_setup_toolchain.sh` fetches Mathlib's prebuilt cache and fails if any Mathlib module had to be compiled locally, and reading the project files (02 and 04) refuses a manifest with no package named `mathlib`.
- A project whose own files use Lean's module system (a file that starts with `module`). `09_kernel_replay.sh` reports the extra compiled parts such files have (`.olean.server`, `.olean.private`) and never says the replay is complete.
- A statement check other than "the primary theorem's type is exactly this constant". The stronger form is a challenge file and Comparator ([`../docs/related-work.md`](../docs/related-work.md)).
