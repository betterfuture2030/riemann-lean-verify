# Another target's runs

Records of the two runs of [`../../../cloud/gcp/target_guest.sh`](../../../cloud/gcp/target_guest.sh), the launcher's modes `target-rehearsal` and `target`. Both were made on 2026-11-27, for the target `grh-compact` ([`../../../targets/grh-compact/`](../../../targets/grh-compact/)): the compact edition of the shorter proof published on 2026-11-25 at <https://github.com/lsernau/grh-lean>, at commit `72fead1`. The script runs this repository's numbered steps for that target on one rented machine, as a person following [`../../../docs/adapting-to-another-proof.md`](../../../docs/adapting-to-another-proof.md) would by hand.

**What this is, and what it is not.** It is one run of this repository's own steps on a second archive: the build, the axiom check, and a replay of every compiled module by `leanchecker`. It is not the community's record of that proof, which is at <https://math.mit.edu/~drew/shortgrh/> and holds checks that were not made here: an export of the proof, independently written kernels, and `lake comparator`. It is also not a sealed run. One user on the machine ran the build and the checks and owned the toolchain, so every status from step 04 on is that user's word ([`../../../cloud/gcp/README.md`](../../../cloud/gcp/README.md), "Another target", says what stands against that and what does not).

`target_facts.json` is a list of facts, not a verdict. Nobody but the scripts and AI agents has yet checked these files against each other.

| Run | Outcome | Machine time | Recorded cost |
|---|---|---|---|
| `target-rehearsal-20261127-123601` | Every phase ran: four small modules compiled (three by step 04's smoke build, one more by step 05), `08 --probe` run on one lemma, two modules replayed | 376 seconds in the ledger (from just before the launcher asked for a machine until it had checked that the machine was gone), on an 8-vCPU machine | 0.04 USD at that machine's ledger rate of 0.40 USD an hour |
| `target-20261127-124345` | Every step ended with status 0: 794 of 794 modules built, the axiom check and its `--deep` walk passed, `leanchecker` passed every module | 2,730 seconds in the ledger, counted the same way (45.5 minutes), on a 16-vCPU machine | 0.57 USD at that machine's ledger rate of 0.75 USD an hour |

Both rows are in [`../ledger.tsv`](../ledger.tsv). The ledger's rates are rounded up from list prices; the bill is the authority.

## `target-20261127-124345`

Launched on 2026-11-27 at 18:43:49 UTC (the ledger's time, written just before the launcher asked for a machine; `us-central1-a` had none and `us-central1-b` gave it), from commit `2102d95`: one `n4d-standard-16` machine (16 vCPUs, which are 8 cores with two threads each; 62 GB of memory as the machine reports it) in `us-central1-b`, on demand, with Ubuntu 24.04.5. The guest's script reached its end at 19:26:06 UTC, 2,487 seconds after it started (`target_facts.json`); its final `status.json` is stamped six seconds later. The machine was gone by 19:29:19 UTC. It was the second run of this script on a rented machine; the first was the rehearsal below, eight minutes earlier, from the same commit.

|---|---|

The build was not sandboxed. How much memory it used was not measured: the peak figures in `steps.tsv` are each the largest single process of a step, and the build has none there. It ended with status 0 and no failed job, on a machine with 62 GB.

## `target-rehearsal-20261127-123601`

Launched at 18:36:05 UTC (the ledger's time; `us-central1-a` had no machine here either) from the same commit: one `n4d-standard-8` machine (8 vCPUs, 31 GB as reported) in `us-central1-b`. The guest's script reached its end 141 seconds after it started (its final `status.json` says 147). It was the first run of the script on a real machine. Before it the script's control flow had been tried only with stand-ins ([`scripts/dev/test_target_guest.sh`](../../../scripts/dev/test_target_guest.sh)).

- Steps 00 to 04 as in the run above, with the same results; step 04 took 72 seconds.
- Step 05 was asked for the profile's two smoke modules and one more, `Lib.General.LinearAlgebra.SubmersionZero`: it compiled that one after the network had been taken away: 6 seconds by the build's own status file (18:38:21 to 18:38:27 UTC), of which Lake gives 2.6 to the module. The 34 seconds in `target_facts.json` (`build_seconds`) is the script's own timing, which includes the 30 seconds it waits between looks at the build. Four compiled modules in all.
- `08 --probe` on the lemma `rootDiscr_pos` of `Lib.General.Analysis.ZpowSum`: exit status 1, with lean's own exit status 0. The 1 is the probe saying that this lemma's conclusion is not the constant `RiemannHypothesis`, which it is not; lean's 0 shows that step 08's check file, written for the default target's toolchain, is read by this target's Lean 4.35.0. That was the point of running it before the full build.
- `09 --sample 2`: `leanchecker` passed both sampled modules.
- Compiled files and toolchain files unchanged across the checks.

A rehearsal says nothing about the proof.

## Files

In each run's directory: `target_facts.json` and `facts.tsv` (the same facts, as they were recorded), `steps.tsv` (each step's exit status, seconds and peak memory in kB), `status.json`, `phases.tsv` (when each phase began, in seconds since 1970), `env.txt` (the machine), `heartbeat`, `pilot.log` (the script's own log), and `launch.log` and `watch.log` (what the launcher printed on the owner's machine, the deletion of the machine included; the clock times in `watch.log`, like those in the runs' names, are the owner's local time, not UTC, and the "2.00 USD/h" in its last line is the launcher's default rate in a fixed message, not the rate of these two rows).

In `logs/`: each step's output as the guest saw it (`00_prereqs.log` to `09_summary.log`, `import_graph.log` and `reproduce.log`); the steps' own logs (`download.log`, `setup-<time>.log`, `reproduce_*.log`, `axioms-*.log`, `build-status.txt`, the build log); step 08's summaries (`axioms-full.json` and `axioms-full-deep.json` in the run, with the `--deep` walk's count for each module in `axioms-full-<time>.modules.tsv.gz`; `axioms-probe.json` in the rehearsal); `replay_summary.json` and `replay_results.tsv.gz`, step 09's summary and its result for every module it checked; `compiled_before.sha256` (gzipped in the run's directory), the compiled files and their hashes; `disk.txt`, the size and use of the data disk at the end; and the records the steps keep of where the tree came from (`source.tar.from`, `extract.from`, `rh-target`, `import_graph_summary.json`).

They are kept with the runs' results on the owner's disk and in the bucket.

The files here were copied through `scripts/dev/scrub.py clean` ([`../../README.md`](../../README.md)); it changed six files in each run. In `logs/00_prereqs.log`, `logs/04_setup.log`, `logs/09_replay_1.log` and `logs/setup-<time>.log` the home directory of the machine's user now reads `<HOME>`. In `launch.log` and `watch.log` it replaced the owner's home directory and work directory (`<HOME>`, `<WORKDIR>`). The names of the project and the bucket in those two files had already been replaced as the launcher's output was saved, and read `<PROJECT_ID>` and `<BUCKET>` as elsewhere in `records/`; the addresses of the two machines in `launch.log` were replaced by hand afterwards (`<INTERNAL_IP>`, `<EXTERNAL_IP>`). Files of more than 100 kB were gzipped after that (three, all in the run's `logs/`), and the two files the guest had gzipped, the build log and the replay's results, were unpacked, cleaned and gzipped again.
